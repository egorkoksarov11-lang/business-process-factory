# AGENTS — единые правила работы агентных чатов

Этот файл является обязательной точкой входа для любого чата/агента, работающего с репозиторием.

## 1. Назначение репозитория

Репозиторий управляет конвейером преобразования сырых интервью и иных источников в:

1. согласованную архитектуру процессов;
2. подтвержденные модели AS-IS;
3. анализ проблем и причин потерь;
4. организационно оптимизированные модели TO-BE;
5. сквозные схемы и детальные подпроцессы;
6. Visio/PDF и обязательные приложения к схемам;
7. историю изменений с объяснением, почему AS-IS был преобразован именно так.

GitHub — источник истины. Переписка агента не является источником истины.

## 2. Четыре рабочие роли

Агент должен работать только в одной из ролей на конкретной стадии:

- `01 Coordinator / Process Architect` — `agents/01_COORDINATOR_PROCESS_ARCHITECT.md`;
- `02 AS-IS Analyst` — `agents/02_AS_IS_ANALYST.md`;
- `03 Improvement / TO-BE Architect` — `agents/03_IMPROVEMENT_TO_BE_ARCHITECT.md`;
- `04 Modeler / QA` — `agents/04_MODELER_QA.md`.

Не дробить работу на дополнительные микророли без явной необходимости. Один агентный блок должен получать осмысленный вход и выдавать законченный, проверяемый результат.

## 3. Что прочитать перед началом работы

Каждый агент обязан:

1. прочитать этот файл;
2. прочитать свою инструкцию в `agents/`;
3. прочитать `governance/WORKFLOW.md`;
4. прочитать `governance/PROCESS_ARCHITECTURE_RULES.md`;
5. для детального AS-IS и последующих стадий — `governance/DATA_MODEL_V1_1.md`;
6. при работе со схемами — `governance/QUALITY_STANDARD.md`;
7. открыть `registry/process_registry.yaml` и пакет текущего процесса;
8. проверить `open_questions` и блокирующие замечания предыдущей стадии.

## 4. Основные правила

### 4.1 Не выдумывать AS-IS

В AS-IS разрешены только:

- `EXPLICIT` — прямо подтвержденные источником факты;
- `INFERRED` — осторожные выводы, явно помеченные как вывод;
- `UNKNOWN` — неизвестные сведения, требующие уточнения;
- `CONFLICT` — противоречащие друг другу источники.

Нельзя превращать нормальную практику, отраслевое знание или предположение агента в факт текущего процесса.

### 4.2 Не перезаписывать историю

AS-IS сохраняется как самостоятельный исторический слой. TO-BE не заменяет и не «исправляет» AS-IS.

Каждое существенное изменение TO-BE должно иметь запись в `change_log`:

`AS-IS → проблема → решение → причина → ожидаемый эффект → TO-BE`.

### 4.3 Один канонический процесс — много представлений

Процесс существует один раз в `processes/<PROCESS_ID>/`, но может отображаться в нескольких `views`:

- карте деятельности сотрудника;
- карте подразделения;
- карте функции;
- межфункциональном end-to-end процессе;
- клиентском ландшафте процессов.

Не копировать один и тот же процесс как независимые процессы только потому, что его описали разные интервьюируемые.

### 4.4 Уровни детализации

Использовать:

- `L0` — landscape / верхнеуровневая цепочка;
- `L1` — сквозной межфункциональный процесс;
- `L2` — подробный подпроцесс;
- `L3` — только если L2 объективно невозможно сделать читаемым.

Обычные `previous/next` не должны смешивать уровни. Cross-level переходы фиксируются через parent boundary/handoff.

### 4.5 Граница процесса

Самостоятельный процесс обычно имеет:

- осмысленный триггер;
- собственный бизнес-результат;
- понятного потребителя результата;
- устойчивую границу относительно соседних процессов.

Техническая операция, канал коммуникации, перенос файла или единичное действие сами по себе не должны становиться отдельным бизнес-процессом без самостоятельного результата.

### 4.6 TO-BE: сначала организация, потом автоматизация

Основной TO-BE должен быть реализуем без обязательного IT/AI-проекта и в первую очередь использовать:

- устранение дублей;
- сокращение лишних передач;
- ясное распределение ответственности;
- чек-листы и критерии контроля;
- разумное параллельное выполнение;
- единые точки входа и каналы;
- SLA и правила эскалации;
- устранение повторных проверок и повторного ввода.

Автоматизация фиксируется отдельными рекомендациями и не должна маскировать плохую организационную логику.

## 5. Обязательная прослеживаемость

Для значимых элементов должна сохраняться цепочка:

`source_ref/segment → evidence fact → as_is_step/flow/handoff/information_object → issue/change → to_be_step → diagram_element → attachment`.

Если связь невозможно восстановить, работа считается незавершенной.

## 6. Информационные объекты, документы и сообщения

Процессная модель должна сохранять значимые объекты обмена, а не только действия.

Различать:

- документ;
- сообщение;
- запрос;
- уведомление;
- файл;
- отчет;
- запись/набор данных;
- систему;
- канал;
- handoff.

Пример: `электронная почта` — канал, `письмо с заявкой` — message/request, `HelpDesk` — система, `заявка №...` — запись/информационный объект.

Если сообщение или документ влияет на переход, согласование, ожидание или подтверждение результата — его нельзя терять в свободном тексте.

Если TO-BE вводит новый документ, шаблон, чек-лист, реестр или форму, этот артефакт должен реально существовать в `documents/` соответствующего процесса.

Документная классификация:

- `EXISTING_INTERNAL` — внутренний документ заказчика: не создавать заново, только ссылаться;
- `EXTERNAL_STATUTORY` — внешний/нормативный документ: не изобретать;
- `TRANSACTIONAL` — конкретный экземпляр документа в ходе процесса: шаблон не обязателен;
- `PROPOSED_TEMPLATE` — новый шаблон: обязательно создать;
- `PROPOSED_CHECKLIST` — новый чек-лист: обязательно создать;
- `PROPOSED_REGISTER` — новый реестр: обязательно создать.

## 7. Правила схем

Схема должна одновременно быть подробной и не перегруженной.

Нельзя:

- дробить одно бизнес-действие на интерфейсные микрошаги без бизнес-смысла;
- объединять шаги, если между ними меняется роль, результат, контроль, документ/сообщение, состояние или возможная ветка;
- уменьшать шрифт ради размещения содержимого;
- допускать выход текста за объект;
- накладывать объекты друг на друга;
- оставлять непонятные пересечения линий;
- использовать неопределенные роли вроде «сотрудник», если роль может быть установлена точнее.

Каждый процесс должен иметь:

- вход/триггер;
- ссылку на предыдущий процесс, если он есть;
- четкий результат;
- ссылку на следующий процесс/потребителя;
- конкретные роли;
- понятные условия ветвления;
- необходимые пояснения и приложения.

## 8. Состояния конвейера

Канонические статусы:

`NEW → ARCHITECTURE_READY → AS_IS_DRAFT → CLARIFICATION_REQUIRED → AS_IS_READY → TO_BE_DRAFT → TO_BE_READY → MODELING → QA_REQUIRED → CLIENT_READY → APPROVED`

Переходы и критерии — в `governance/WORKFLOW.md`.

## 9. Версии схемы данных

`schema_version: "1.0"` остается допустимой для уже созданных architecture packages.

v1.1 применяется прежде всего к насыщенному AS-IS и последующим стадиям. Нельзя заставлять активный Agent 01 переписывать архитектуру только из-за обновления data contract.

## 10. Правило завершения работы агента

Перед завершением стадии агент обязан:

1. сохранить результат в репозитории;
2. обновить статус процесса;
3. перечислить нерешенные вопросы;
4. зафиксировать, что именно изменилось;
5. указать следующий ожидаемый агентный блок;
6. не оставлять критически важный результат только в чате.
