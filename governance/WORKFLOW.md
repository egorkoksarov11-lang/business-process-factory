# Workflow — управление конвейером

## 1. Общий маршрут

`Sources → Architecture → AS-IS → Improvement/TO-BE → Modeling/QA → Client package`

Каждый этап имеет определённый вход, выход и критерий готовности.

## 2. Состояния процесса

### `NEW`
Есть источник, но процесс ещё не классифицирован.

Выход из стадии:
- источник зарегистрирован;
- известны интервьюируемый, роль и подразделение;
- назначены `source_id`.

Следующий блок: Coordinator / Process Architect.

### `ARCHITECTURE_READY`
Определены границы процесса и его место в архитектуре.

Обязательное:
- `process_id`;
- название;
- уровень L0/L1/L2/L3;
- триггер и бизнес-результат на архитектурном уровне;
- предыдущие/следующие процессы, если известны;
- список релевантных источников;
- представления (`views`), в которых процесс участвует;
- определено, не является ли объект операцией/проблемой вместо процесса.

Следующий блок: AS-IS Analyst.

### `AS_IS_DRAFT`
Создана первичная фактическая модель.

Если есть критические пробелы, процесс переводится в `CLARIFICATION_REQUIRED`.

### `CLARIFICATION_REQUIRED`
Есть вопросы, без ответа на которые невозможно корректно завершить AS-IS или принять решение о границе/ветвлении.

Не все UNKNOWN блокируют работу. Блокирующими считаются неизвестные, которые меняют:
- границу процесса;
- исполнителя;
- порядок передачи ответственности;
- ключевое решение;
- обязательный документ;
- вход/выход;
- значимый сценарий исключения.

После ответа — возврат в `AS_IS_DRAFT`.

### `AS_IS_READY`
Фактическая модель завершена настолько, насколько позволяют источники.

Gate:
- все шаги имеют роли;
- вход и результат понятны;
- ветвления описаны;
- источники привязаны;
- INFERRED и UNKNOWN не смешаны с фактами;
- противоречия источников зафиксированы, а не скрыты;
- нет оптимизации внутри AS-IS.

Следующий блок: Improvement / TO-BE Architect.

### `TO_BE_DRAFT`
Созданы диагностика, набор изменений и первичная TO-BE модель.

### `TO_BE_READY`
TO-BE логически утверждён для моделирования.

Gate:
- каждое существенное изменение имеет причину;
- основной TO-BE организационный, а не зависимый от автоматизации;
- сохраняется прослеживаемость к AS-IS;
- определены новые документы/чек-листы;
- нет лишних согласований и микрошагов;
- роли конкретны;
- определены необходимые SLA/правила эскалации, если они вводятся;
- все рекомендации автоматизации отделены от core TO-BE.

Следующий блок: Modeler / QA.

### `MODELING`
Строятся L1/L2 схемы, приложения, клиентские представления и экспортные форматы.

### `QA_REQUIRED`
Модель создана, но должна пройти финальную проверку.

Проверяются два слоя:

**Semantic QA**
- соответствие Process Package;
- корректность ролей;
- входы/выходы;
- логика gateway;
- отсутствие потерянных веток;
- наличие обязательных документов;
- трассировка изменений.

**Visual QA**
- читаемость;
- шрифт;
- отсутствие наложений;
- отсутствие выхода текста за фигуры;
- отсутствие визуально неоднозначных линий;
- разумный размер страницы;
- эстетическая целостность;
- достаточные пояснения без перегруза.

### `CLIENT_READY`
Сформирован полный пакет:
- VSDX, если требуется;
- PDF;
- приложения;
- паспорт процесса;
- при необходимости — Change Summary;
- ссылки на соседние процессы.

### `APPROVED`
Результат принят заказчиком/владельцем проекта.

После approval изменения выполняются новой версией, а не перезаписью истории.

## 3. Единица передачи между агентами

Агенты передают не «сообщение», а обновлённый `Process Package`.

Минимальный handoff должен содержать:
- `process_id`;
- текущий статус;
- изменённые файлы;
- известные блокеры;
- нерешённые вопросы;
- решение, ожидаемое от следующей роли.

## 4. Работа с несколькими интервью

Интервью организованы по источникам, а не по процессам. Один источник может раскрывать несколько процессов; один процесс может подтверждаться несколькими интервью.

Coordinator обязан:
1. искать совпадающие процессы между интервью;
2. не создавать дубли только из-за другого рассказчика;
3. объединять evidence при сохранении авторства каждого утверждения;
4. фиксировать противоречия;
5. определять, где более детальное интервью раскрывает L2 уже существующего L1.

## 5. Управление изменениями после нового интервью

Новое интервью не уничтожает существующую версию.

Порядок:
1. добавить новый source;
2. обновить evidence;
3. определить затронутые процессы;
4. создать новую версию AS-IS при изменении фактов;
5. пересмотреть только связанные изменения TO-BE;
6. обновить change log;
7. повторно выполнить QA затронутых схем.

## 6. Definition of Done процесса

Процесс считается готовым к клиенту только если:
- он находится в корректном месте архитектуры;
- AS-IS сохранён;
- TO-BE объясним;
- история преобразований доступна;
- схемы читаемы;
- новые документы реально приложены;
- ссылки на предыдущий/следующий процесс не противоречат общей карте;
- нет критических `UNKNOWN`, скрытых как факт;
- реестр обновлён.
