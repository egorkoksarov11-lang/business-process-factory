# Process Architecture Rules

## 1. Цель

Определить единые правила, по которым интервью превращаются в устойчивую архитектуру процессов, а не в набор схем «по рассказчикам».

## 2. Три разных объекта, которые нельзя смешивать

### Process Landscape
Карта деятельности роли/подразделения: показывает, в каких процессах участвует сотрудник или функция.

Пример: «Главный бухгалтер» → первичные документы, банки, налоги, зарплата, отчетность, договоры, проверки.

### End-to-End Process
Сквозной процесс достижения бизнес-результата через несколько ролей/подразделений.

Пример: «Потребность в сотруднике → подбор → оформление → выход → адаптация».

### Detailed Subprocess
Подробное раскрытие одного блока end-to-end процесса.

Пример: «Формирование и согласование заявки на подбор».

Один канонический процесс может входить в несколько landscape/view, но не дублируется как отдельная сущность.

## 3. Уровни

### L0
Используется для:
- карты деятельности сотрудника;
- карты подразделения;
- верхнеуровневой цепочки ценности;
- навигации между L1 процессами.

На L0 не показываются интерфейсные действия и мелкие исключения.

### L1
Сквозной межфункциональный процесс. Обычно содержит несколько ролей и крупные бизнес-шаги/подпроцессы.

L1 должен позволять понять процесс от триггера до бизнес-результата без открытия L2, но не обязан показывать каждую операционную деталь.

### L2
Детальный подпроцесс. Показывает конкретные действия, решения, документы, исключения и возвраты, необходимые для выполнения L1 блока.

### L3
Допускается, когда L2 объективно становится нечитаемым или содержит отдельный сложный регламентированный механизм. Не использовать L3 ради формальной декомпозиции.

## 4. Тест самостоятельного процесса

Кандидат считается самостоятельным процессом, если большинство ответов «да»:

1. Есть собственный триггер?
2. Есть самостоятельный бизнес-результат?
3. Есть потребитель результата?
4. Можно разумно определить начало и завершение?
5. Процесс может изменяться/регламентироваться отдельно?
6. Он не является только техническим действием другого процесса?

Если бизнес-результат отсутствует, объект чаще является операцией, подпроцессом, правилом или проблемой.

## 5. Примеры классификации

- «Оформление приема сотрудника» — процесс/L1 или L2 в зависимости от общей архитектуры.
- «Внести данные в 1С» — операция.
- «Перенести файл между серверами» — техническая операция / cross-process pain point, если нет отдельного бизнес-результата.
- «Ежегодная сверка воинского учета» — самостоятельный циклический процесс, если имеет отдельный календарный триггер и результат.
- «Проверка комплектности документов» — шаг/контроль, а не самостоятельный процесс, если его результат нужен только для продолжения текущего процесса.

## 6. Гранулярность шага

Хороший шаг описывает:

`конкретная роль + бизнес-действие + объект + наблюдаемый результат`.

Шаг следует разделить, если между частями меняется хотя бы одно:
- исполнитель;
- ответственность;
- состояние объекта;
- обязательный документ;
- контроль/решение;
- возможное ветвление;
- точка ожидания/передачи.

Шаги следует объединить, если они являются последовательностью технических микродействий одной роли без отдельного бизнес-результата.

## 7. Роли

В реестре ролей используется каноническое название и aliases.

Предпочтительно:
- `Ведущий специалист по кадровому делопроизводству`;
- `Главный бухгалтер`;
- `Директор по персоналу`.

Нежелательно:
- `HR` при наличии конкретной роли;
- `кадровик`, если известна должность;
- `сотрудник`, если роль можно определить;
- имя физического лица вместо функциональной роли.

Имя интервьюируемого хранится в metadata источника, а не используется как lane процесса.

## 8. Вход, выход и соседние процессы

Каждый L1/L2 обязан содержать:
- `trigger`;
- `input`;
- `previous_process`, если применимо;
- `business_result`;
- `consumer`;
- `next_process`, если применимо.

Вход и выход должны образовывать единую цепочку общей архитектуры, а не быть декоративными start/end events.

## 9. Cross-process проблемы

Проблемы, встречающиеся во многих процессах, хранятся как сквозные ограничения, а не копируются как самостоятельные процессы.

Примеры:
- несколько мессенджеров;
- неясное распределение функций;
- перенос файлов между серверами;
- отсутствие единой структуры папок;
- отсутствие SLA согласования.

Связь таких проблем с конкретными процессами фиксируется через ссылки.

## 10. Принцип минимально достаточной схемы

Схема должна показывать всё, что нужно для понимания и исполнения процесса, но не обязана показывать:
- клики;
- открытие вкладок;
- распечатку как отдельный шаг, если она не является значимым результатом;
- очевидные технические переходы без изменения состояния.

Если исключение, документ, контроль или передача ответственности меняют поведение процесса — они должны быть отражены.
