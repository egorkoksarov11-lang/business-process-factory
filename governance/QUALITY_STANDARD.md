# Quality Standard — требования к итоговым процессам и схемам

## 1. Общий критерий

Итог должен позволять человеку, не участвовавшему в интервью, понять:
- что запускает процесс;
- кто что делает;
- какие решения принимаются;
- какие документы и системы используются;
- где возникают ожидания/возвраты;
- чем процесс заканчивается;
- куда передаётся результат дальше.

При этом схема не должна быть перегружена очевидными микродействиями.

## 2. Семантическое качество

Обязательно:
- конкретные роли;
- явный trigger;
- явный business result;
- предыдущий/следующий процесс, если есть;
- все значимые ветви;
- все значимые возвраты;
- документы, влияющие на принятие решения или передачу результата;
- различение факта, вывода и неизвестного;
- отсутствие выдуманных SLA, ролей, систем или документов в AS-IS.

## 3. Критерий детализации

Шаг не должен быть настолько крупным, что скрывает смену ответственности или бизнес-решение.

Шаг не должен быть настолько мелким, что показывает интерфейсную механику без отдельного результата.

Проверочный вопрос: «Если убрать этот шаг со схемы, станет ли менее понятно, кто создаёт бизнес-результат, принимает решение, контролирует качество, передаёт ответственность или обрабатывает исключение?» Если нет — шаг, вероятно, лишний.

## 4. Визуальное качество

Обязательно:
- текст полностью помещается в фигурах;
- объекты не перекрываются;
- линии не проходят поверх текста и объектов;
- соединения визуально однозначны;
- направления потока легко считываются;
- lane достаточно высокие для содержимого;
- схема не требует масштабирования до нечитаемого размера;
- одинаковые сущности оформлены одинаково;
- номера шагов последовательны на одном уровне детализации.

### Шрифт

Базовое правило: основной текст схемы не меньше 11 pt при целевом клиентском масштабе. Нельзя уменьшать шрифт, чтобы «впихнуть» схему. Если содержимое не помещается — изменить layout или декомпозировать процесс.

### Плотность

Если L1 превращается в полотно из множества детальных узлов, вынести подробности в L2. Если L2 всё ещё нечитаем — рассмотреть L3, но только как исключение.

## 5. Подписи gateway

Каждое логическое решение должно иметь понятный вопрос/критерий. Исходящие ветви должны быть подписаны понятными значениями, например `Да / Нет`, а не оставаться безымянными.

Не использовать gateway для простого последовательного перехода.

## 6. Документы и поясняющие плашки

На схеме документ показывается тогда, когда он:
- является входом/результатом шага;
- используется для проверки/решения;
- передаётся между ролями;
- нужен клиенту для понимания процесса.

Если документ новый и предложен TO-BE, он обязан быть приложен физически.

Поясняющая плашка допустима для:
- состава комплекта документов;
- критериев проверки;
- SLA/эскалации;
- различий по типам сценариев;
- правил, которые перегрузили бы основной flow.

Плашка не должна дублировать текст основного блока.

## 7. Клиентский комплект

Минимальный пакет для готового процесса:
- актуальная TO-BE схема;
- PDF для просмотра;
- VSDX, если требуется договорённостью;
- все `PROPOSED_*` документы;
- паспорт процесса;
- при необходимости краткий change summary.

AS-IS хранится в репозитории обязательно, даже если не входит в клиентский пакет.

## 8. QA checklist

Перед `CLIENT_READY` проверить:

### Логика
- [ ] Есть start/trigger.
- [ ] Есть результат/end.
- [ ] Указана связь с соседними процессами.
- [ ] Все роли конкретны.
- [ ] Нет потерянных веток.
- [ ] Все возвраты логичны.
- [ ] Нет оптимизационных догадок в AS-IS.
- [ ] Все TO-BE изменения объяснены.

### Документы
- [ ] Каждый новый чек-лист существует.
- [ ] Каждый новый шаблон существует.
- [ ] Внутренние документы заказчика не изобретены заново.
- [ ] Названия документов согласованы между схемой и package.

### Визуал
- [ ] Текст не выходит за фигуры.
- [ ] Нет перекрытий.
- [ ] Нет неоднозначных пересечений линий.
- [ ] Шрифт читаем.
- [ ] Нет чрезмерно длинной/широкой страницы без причины.
- [ ] Подпроцессы вынесены там, где это улучшает читаемость.
