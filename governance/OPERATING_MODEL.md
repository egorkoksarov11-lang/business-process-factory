# Operating Model — как пользоваться репозиторием

## 1. Источник истины

Репозиторий хранит каноническое состояние процессов. Чаты используются как рабочие исполнители стадий.

Никакое существенное решение не считается принятым, пока оно не отражено в файлах репозитория.

## 2. Основные сущности

- `Source` — интервью, анкета, документ, существующая схема.
- `Process` — канонический бизнес-процесс/подпроцесс.
- `View` — представление нескольких процессов: landscape или end-to-end.
- `Role` — каноническая роль и её aliases.
- `Issue` — проблема/потеря AS-IS.
- `Change` — обоснованное преобразование AS-IS → TO-BE.
- `Document` — внутренний, внешний или предложенный артефакт процесса.
- `Process Package` — полный пакет одного процесса.

## 3. Каталоги

- `sources/` — исходные материалы и их metadata;
- `registry/` — общие реестры;
- `processes/` — по одной папке на канонический процесс;
- `views/` — карты ролей, подразделений и сквозные цепочки;
- `templates/` — эталонные структуры;
- `agents/` — инструкции рабочим чатам;
- `governance/` — правила управления;
- `examples/` — проверенные примеры.

## 4. Именование

Рекомендуемый process ID:

`<DOMAIN>-<OBJECT>-<NNN>`

Примеры:
- `HR-RECRUIT-001`;
- `HR-HIRE-001`;
- `ACC-PRIMARY-001`;
- `ACC-REPORTING-001`.

ID стабилен и не меняется из-за переименования процесса.

Source ID:
`SRC-<DOMAIN>-<NNN>`.

View ID:
`VIEW-<DOMAIN>-<NNN>`.

Change ID:
`CHG-<PROCESS_ID>-<NNN>`.

Issue ID:
`ISS-<PROCESS_ID>-<NNN>`.

Document ID:
`DOC-<PROCESS_ID>-<NNN>`.

## 5. Рекомендуемая структура process package

```text
processes/<PROCESS_ID>/
├── process.yaml
├── evidence.yaml
├── as_is.yaml
├── issues.yaml
├── change_log.yaml
├── to_be.yaml
├── open_questions.yaml
├── documents/
├── diagrams/
│   ├── as_is/
│   └── to_be/
└── delivery/
    └── manifest.yaml
```

Файлы создаются по мере прохождения стадий; пустые артефакты заранее не обязательны.

## 6. Версионирование

История Git является технической историей изменений, но внутри process package также хранится доменная версия:
- `as_is_version`;
- `to_be_version`;
- дата и причина ревизии.

Новый источник может изменить AS-IS. В этом случае фиксируется новая версия и ссылка на источник.

## 7. Рабочий цикл чатов

1. Пользователь/координатор добавляет новый source.
2. Agent 01 обновляет registry и архитектуру.
3. Agent 02 формирует AS-IS и вопросы.
4. После достаточного AS-IS Agent 03 формирует issues/change log/TO-BE.
5. Agent 04 выпускает схемы и приложения.
6. После согласования статус становится `APPROVED`.

## 8. Pull Requests и review

При значительном изменении архитектуры или правил рекомендуется работать через отдельную ветку и PR. Небольшие обновления конкретного process package допускаются прямыми commits при одиночной работе, если сохраняется audit trail.

Для клиентски утверждённых процессов рекомендуется изменять через PR, чтобы явно видеть diff.

## 9. Что не хранить как единственный артефакт

Нельзя оставлять только:
- картинку схемы без process package;
- чат без записи решений;
- TO-BE без AS-IS;
- новый чек-лист только как текст внутри фигуры;
- список процессов без связей и уровней.
