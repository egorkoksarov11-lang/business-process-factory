## Цель

Провести первичный архитектурный synthesis IT-функции: определить канонические L1/L2, границы, Role/Function Landscape, E2E views, cross-domain handoffs, architecture candidates и проблемы. **Не строить детальный AS-IS, BPMN, TO-BE и оптимизацию.**

## Ключевая гипотеза источника — проверить, а не принять автоматически

Интервьюируемый прямо выделяет два крупных направления:

1. архитектурные решения / безопасность / развитие инфраструктуры;
2. техническая поддержка пользователей.

Проверь, действительно ли это два L1 либо один из блоков является governance/capability с несколькими самостоятельными процессами. Не создавай отдельный процесс для каждого перечисленного объекта инфраструктуры (серверы, телефония, видеонаблюдение, почта, сайты и т. д.) без trigger/result/consumer.

## Boundary review — техническая поддержка

Архитектурно разложи описанный поток обращения пользователя:

- обращение сотрудника;
- текущие каналы: личный кабинет, телефон, email;
- регистрация заявки в HelpDesk;
- присвоение номера/подтверждение приема;
- взятие в работу;
- временное либо постоянное решение;
- завершение/доработка временного решения;
- повторяющиеся и дублирующиеся обращения.

Определи, что является одним L1, какие блоки достойны L2, а какие являются операциями/правилами/исключениями. Не дроби канал подачи заявки на отдельные процессы.

Зафиксируй заявленный ориентир/показатель `30 минут` и фактическое наблюдение `10–15 минут` строго как данные интервью. Не интерпретируй автоматически, что это формальный SLA, если источник этого однозначно не подтверждает.

Бот из корпоративного мессенджера находится **в разработке**. Не включай его в действующий AS-IS; сохрани как future/planned capability evidence.

## Boundary review — архитектурные решения

Источник описывает широкий и частично самоинициируемый контур архитектуры/безопасности. Не пытайся искусственно детализировать его без данных. Проверь кандидатов, например:

- инициирование/выявление необходимости изменения IT-архитектуры;
- проектирование архитектурного/безопасностного решения;
- внедрение изменения;
- регламентирование повторяющихся требований;
- эксплуатационный handoff/support.

Если trigger/result/consumer недостаточно описаны — оставь architecture candidate / `BOUNDARY_UNKNOWN`, а не придумывай L1.

## Сквозная связь с HR — обязательно сохранить

Интервью содержит важный cross-domain кейс приема и увольнения сотрудников:

- подготовка доступов к выходу сотрудника;
- риск отсутствия уведомления IT о новом сотруднике;
- риск отсутствия уведомления IT об увольнении и сохранения доступов;
- закрепление/открепление техники;
- электронные акты приема/сдачи техники;
- неопределенность ответственной роли между секретарем/кадрами;
- попытка внедрить общий процесс, которая полностью не прижилась.

Это **не основание переписывать HR-HIRE/HR-TERM в этой ветке**. Создай cross-domain handoff/candidate/issue и source evidence, чтобы после merge был отдельный synthesis HR ↔ IT.

Отдельно различай:

- электронные акты по технике — описаны как внедренные и работающие/прижившиеся;
- общий процесс трудоустройства/увольнения — описан как не прижившийся;
- фактическая практика уведомления IT — проблемная/нестабильная.

Не объединяй эти статусы в одну оценку.

## Регламенты и безопасность

Факт наличия попыток писать регламенты и проблема их непрочтения/повторных вопросов сохраняются как governance/problem evidence. Не создавай отдельный L1 на каждый регламент или правило паролей.

## Landscapes / views

Создай Role Landscape интервьюируемой IT-роли, но учти нестандартный статус: внешний руководитель собственной IT-компании с высокой вовлеченностью. Не выдумывай штатную должность или официальное подразделение.

Если целесообразно, создай `FUNCTION_LANDSCAPE` IT-функции с двумя крупными направлениями и архитектурными кандидатами. Это не последовательный E2E.

Создай E2E для технической поддержки только если подтверждается реальная multi-process цепочка; не называй обычный один L1 с внутренними L2 multi-process E2E без основания.

## Роли и системы

Нормализуй только подтвержденные роли/сущности. Проверь:

- IT lead / внешний IT-руководитель;
- сотрудники технической поддержки его компании;
- внутренний сотрудник/пользователь;
- HelpDesk как система;
- личный кабинет как канал/interface к support, если источник не доказывает отдельную систему;
- email/телефон/корпоративный мессенджер как каналы;
- возможные HR/секретарь как cross-domain роли в onboarding/offboarding — с UNKNOWN там, где источник колеблется.

Не нормализуй имя «Анатолий» в бизнес-роль: должность в интервью не названа.

## Выходные артефакты

Создай в своей ветке:

- source-specific architecture evidence;
- process packages для обоснованных L1/L2;
- Role Landscape и при необходимости IT Function Landscape;
- E2E view(s) только при достаточном основании;
- cross-domain HR↔IT handoff/candidates/issues;
- architecture candidates по недостаточно раскрытому архитектурному контуру;
- handoff `Agent 01 → Agent 02` для IT scope;
- изменения registry/role/system dictionaries только по своему домену.

Перед финализацией PR подтяни актуальный `main` и **не перезаписывай чужие записи в общих registry-файлах**. Сохрани все HR/accounting записи, появившиеся к этому моменту.
