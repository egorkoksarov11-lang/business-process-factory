# Handoff Agent 01 → Agent 02 — HR synthesis 001

## Scope

Архитектурный synthesis выполнен по двум источникам:

- `SRC-HR-KDP-001` — интервью ведущего специалиста по кадровому делопроизводству;
- `SRC-HR-DIR-001` — интервью директора по персоналу.

Детальный AS-IS не создавался. Источники не объединялись в один «усредненный рассказ»: архитектурные факты и source-specific evidence сохранены отдельно в:

- `sources/evidence/SRC-HR-KDP-001_architecture.yaml`;
- `sources/evidence/SRC-HR-DIR-001_architecture.yaml`.

## Каноническая цепочка входа нового сотрудника

Создан реальный multi-process E2E:

`HR-RECRUIT-001 → HR-HIRE-001 → HR-ADAPT-001`

View: `views/VIEW-HR-HIRE-E2E-001.yaml`.

### `HR-RECRUIT-001` — Подбор сотрудника на вакантную позицию

Архитектурная граница:

- trigger: заявка непосредственного руководителя на вакантную позицию;
- result: кандидат выбран и оффер подготовлен; источник подтверждает последующий выход выбранного кандидата;
- next: `HR-HIRE-001`.

Не создавать отдельные L1 для профиля вакансии, размещения на HeadHunter, первого/второго интервью или оффера: это внутренние L2-блоки/операции подбора.

Ключевой UNKNOWN: точка завершения подбора и handoff — выбор кандидата, принятие оффера или подтверждение даты выхода.

### `HR-HIRE-001` — Кадровое оформление приема сотрудника

Граница пересмотрена.

Старый trigger «получение сообщения от директора по персоналу» больше не трактуется как старт всей HR-цепочки. После SRC-HR-DIR-001 это внутренняя передача из `HR-RECRUIT-001` в кадровое оформление.

Сохраняются как L2/операции внутри `HR-HIRE-001`:

- получение/проверка комплекта документов;
- ввод/оформление в 1С;
- ознакомление с ЛНА и подписание кадровых документов;
- отчетность о приеме в СФР;
- условная ветка воинского учета при приеме.

Next: `HR-ADAPT-001`.

Ключевой UNKNOWN: точный момент handoff из подбора и конечная точка приема относительно подтверждения сдачи отчетности в СФР.

### `HR-ADAPT-001` — Сопровождение адаптации и испытательного срока

Новый самостоятельный L1.

- trigger: фактический выход сотрудника и начало адаптации/испытательного срока;
- result: период проконтролирован, получена обратная связь, выявленные негативные моменты в зоне HR отработаны;
- previous: `HR-HIRE-001`.

Не выдумывать поставщика обратной связи, критерии прохождения или действие при неудовлетворительном результате: источник этого не раскрывает.

## `HR-TERM-001` — Прекращение трудовых отношений с сотрудником

Каноническая граница расширена. Старое название «Оформление увольнения сотрудника» было слишком узким относительно двух источников.

Теперь L1 охватывает подтвержденные источниками сценарии прекращения отношений, а не отдельные process_id по каждому основанию:

1. `TERM-SCENARIO-EMPLOYEE-INITIATED` — инициатива сотрудника; `SRC-HR-KDP-001`, существенно более детальный материал.
2. `TERM-SCENARIO-REDUCTION` — сокращение штата/снижение численности; `SRC-HR-DIR-001`, только boundary-level evidence.
3. `TERM-SCENARIO-AGREEMENT` — договоренность с сотрудниками; `SRC-HR-DIR-001`, только boundary-level evidence.
4. Неясный фрагмент `SRC-HR-DIR-001` «по закону дела ЦПТК» — `DO_NOT_MODEL`, не интерпретировать.

Отчетность об увольнении, выдача отдельных документов и условные действия воинского учета остаются частями L1, а не отдельными микропроцессами.

Agent 02 может детализировать AS-IS прежде всего для сценария по инициативе сотрудника. Для сокращения и договоренности нельзя достраивать шаги из отраслевой практики.

## Role Landscapes

Канонические process refs роли КДП:

- `HR-HIRE-001`;
- `HR-TERM-001`;
- `HR-MIL-ORG-001`;
- `HR-MIL-CHANGE-001`;
- `HR-MIL-RECON-001`;

`HR-RECRUIT-001` и `HR-ADAPT-001` не включены: самостоятельное участие КДП в этих процессах текущими источниками не подтверждено.

### `VIEW-HR-DIRECTOR-ROLE-001`

Канонические process refs директора по персоналу:

- `HR-RECRUIT-001`;
- `HR-HIRE-001`;
- `HR-ADAPT-001`;
- `HR-TERM-001`.

Официальное подразделение директора по персоналу — `UNKNOWN`; DEPARTMENT_LANDSCAPE не создавался.

## Что не превращено в отдельные L1

`SRC-HR-DIR-001` перечисляет широкий функционал. После boundary-test не создавались микропроцессы из:

- оформления личных дел;
- отдельных приказов;
- табелирования;
- учета отпусков;
- учета больничного времени;
- отдельных документов/копий;
- отдельных действий согласования.

`Контроль кадрового делопроизводства` классифицирован как cross-process governance responsibility, а не отдельный процесс.
